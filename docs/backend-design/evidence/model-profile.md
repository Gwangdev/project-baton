판정(2026-10-20 갱신): **로컬 Ollama와 OpenAI는 전체 규모로 평가했다. Google은 무료 등급의 하루 호출 한도 때문에 축소 규모(문서 8·질문 8)로만 평가했다.** 아래 「공급자 평가 (2026-10-20)」가 최신이고, 「W13 연결과 평가」는 그 앞의 기록이다. 그 앞의 「환경 차단」 서술은 W07.2 시점(2026-09-24)의 기록이라 역사로 남긴다.

## 확인한 환경 (2026-09-24, 작업 머신)

- 로컬 모델 런타임: `ollama`, `lms`, `llama-server` 명령이 없다. `localhost:11434`(Ollama)와 `localhost:1234`(LM Studio)가 응답하지 않는다.
- 공급자 자격증명: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`, `AZURE_OPENAI_API_KEY`, `SPRING_AI_OPENAI_API_KEY`가 설정되어 있지 않다. 값은 확인하지 않았고 설정 여부만 확인했다.
- 외부 공급자 호출은 합성 데이터라도 외부 전송이므로 사용자 승인 대상이다. LLM 공급자의 데이터 처리 조건도 아직 확인되지 않아 호출하지 않았다(개발 상태 기록(비공개)의 미해결 라벨로 추적 중).

## 현재 고정된 프로필

|---|---|

| 구조화 | 기록된 출력 재생. 키는 문서 본문 SHA-256이고 `backend/src/main/resources/ai-stub/structuring.json`에 fixture 문서 2건이 있다. 그 밖의 문서는 기록 0건 |

## 실모델 도입 절차

1. 로컬 런타임이나 승인된 공급자를 정하고, 해당 Spring AI starter를 `build.gradle.kts`와 `backend/DEPENDENCIES.md`에 추가한다.
2. `BATON_AI_PROFILE=local`(또는 `provider`), `BATON_AI_EMBEDDING_MODEL_ID`, `BATON_AI_CHAT_MODEL_ID`를 설정한다.
3. 임베딩 차원이 256이 아니면 기동이 멈춘다. `record_embeddings`를 새 차원으로 다시 만드는 migration을 추가하고 stub 행을 지운 뒤 다시 임베딩한다. 한 열에 크기를 섞지 않는다.
4. 실제 호출 한 번으로 모델 ID·차원·digest를 확인해 이 문서에 고정한다.
5. 평가 데이터로 구조화 실패율과 평균 처리 시간을 측정한다. 코드 펜스 같은 형식 실패가 많으면 파서를 느슨하게 하지 말고 프롬프트나 모델 설정을 바꾼다.
6. 거리 상한과 HNSW 필요성을 데이터 규모 시험으로 다시 정한다.

## W13 연결과 평가 (2026-10-05)

### 구성
- Spring AI의 공식 starter 세 개(OpenAI, Google GenAI와 그 임베딩, Ollama)를 의존성에 더했다(`backend/DEPENDENCIES.md`). 모델은 환경변수로 고른다: `BATON_AI_PROFILE=local|provider`와 `BATON_AI_PROVIDER=openai|google-genai|ollama`(채팅과 임베딩을 따로 고르려면 `BATON_AI_CHAT_PROVIDER`, `BATON_AI_EMBEDDING_PROVIDER`), 모델 ID는 `BATON_AI_CHAT_MODEL_ID`, `BATON_AI_EMBEDDING_MODEL_ID`. 공급자를 정하지 않으면 모델 bean이 만들어지지 않고 stub이 돈다. 어댑터 코드는 공급자와 무관하다.
- 키는 환경변수 `OPENAI_API_KEY`, `GOOGLE_API_KEY`로만 받는다(사용자가 `~/baton-secrets/ai.env`에 둔다). 필요한 값이 없으면 기동이 멈추고 변수 이름을 말한다(값은 말하지 않는다). OpenAI·Google은 배포 밖이라(배포 네트워크 밖 주소의 Ollama도 같다) `BATON_AI_EXTERNAL_TRANSMISSION=approved`도 명시해야 기동한다(승인 없는 외부 전송은 금지 자동화 행위이므로). 기동 로그에 키 값이 없음을 시험으로 검사한다.
- **기동 때 공급자를 호출하지 않는다.** 이전에는 임베딩 어댑터가 기동할 때 모델에 차원을 물었다(공급자 호출). 지금은 묻지 않는다.
- **임베딩은 256차원으로 맞춘다.** 모델이 더 긴 벡터를 주면(embeddinggemma 768, OpenAI·Google는 기본 더 긺) 앞 256개를 잘라 단위 길이로 다시 맞춘다. 정확히 256이면 그대로, 더 짧으면 거절한다. 어느 공급자든 같은 경로다.
- **임베딩 모델을 바꾸면** 이전 모델의 벡터는 검색에 쓰이지 않는다(검색은 현재 모델 ID의 벡터만 읽는다). 새 모델의 벡터가 없는 확정 기록은 `EmbeddingBackfill`이 주기(기본 60초, 한 번에 200건)로 색인 작업을 만든다.
- Ollama: 채팅은 JSON 모드(`format: json`)와 `temperature: 0`, 생각 출력 끔. 이유는 아래 「발견」.

### 평가 도구
`./gradlew aiEvaluation`(`check`에 들어 있지 않다). 합성 문서 50건(기록 54건과 잡음 문서 4건, 지시문이 든 문서 4건)과 질문 30건(근거 있음 15, 근거 없음 5, 충돌 5, 근거 안의 지시문 5)을 앱의 구조화·답변·임베딩 어댑터에 그대로 넣어, 구조화 성공률·기록 재현율·잡음 문서에서 지어낸 기록·지연, Q&A 정답률(종류별)·인용 검증·지연, 임베딩 검색 recall@3, 사용 토큰을 낸다. 토큰 상한(기본 채팅·임베딩 각 100만)을 호출 전에 확인해 넘을 것 같으면 멈추고 이유를 적는다. 합성으로 표시되지 않은 집합은 어떤 모델에도 보내지 않는다. 데이터는 `tools/make_ai_eval_set.py`가 고정 시드로 만든다. 실행 방법은 `AiEvaluationRun`의 Javadoc에 있다.

README §8의 목표(구조화 p95 30초, 첫 답변 p95 3초, 전체 15초)에 대해 이 로컬 소형 모델은 구조화(p95 8.7초)와 Q&A 지연(p95 2.5초)이 목표 안이다. 단, 이 지연은 한 번에 하나씩 순차로 잰 값이다. 동시 부하에서의 지연과 처리량(NFR-04)은 재지 않았다.

### 발견
1. **작은 로컬 모델은 JSON을 요구해도 평문으로 추론한다.** `qwen3:4b`는 생각 출력을 꺼도 답 안에서 약 1,200토큰의 서술을 한 뒤에야 끝나(첫 평가에서 구조화 평균 118초, Q&A 평균 22초) 엄격한 파서가 모두 거절했다(구조화 0/4, Q&A 0/4). Ollama의 JSON 모드를 켜자 같은 호출이 4~5초로 줄고 Q&A는 7/8이 맞았다.
2. **모델이 `ownerUserId`를 숫자가 아니라 문자열("5")로 냈다.** 파서는 스키마 위반을 고쳐 쓰지 않는다(README §7). 프롬프트에 「숫자로 쓰고 문자열은 안 된다」를 한 줄 더하자 구조화가 0/6에서 8/8(작은 평가)과 46/50(전체)로 올랐다. 파서를 느슨하게 하지 않고 프롬프트로 고쳤다.
3. **남은 구조화 실패와 오류.** 4건은 파서가 거절했다(발췌가 원문과 다른 경우 등으로 보이나 실패 출력의 앞부분만 남겨 원인을 확정하지 못했다). 잡음 문서 4건에서 기록을 지어낸 것은 4건이고 모두 사람이 검토하는 AUTO_DRAFT로만 남는다. 충돌 문항은 두 기록을 모두 말해야 하는데 60%만 그렇게 했다(소형 모델의 한계로 보인다).
4. **embeddinggemma의 256차원 절단은 검색에서 문제가 없었다**(recall@3 100%). 절단이 품질을 크게 해치지 않는다는 뜻이 아니라 이 합성 집합의 질문이 쉽다는 뜻일 수 있다. 실제 문서에서의 검색 품질은 재지 않았다.

### 한계와 가정(검증 지적 99·96)
- **측정은 표본 안이다.** 프롬프트 한 줄을 이 합성 집합을 보며 고쳤고(발견 2) 그 뒤의 점수가 위 표다. 같은 집합으로 고르고 잰 값이라 새 문서에서의 성능은 이보다 낮을 수 있다.
- **검색 recall@3은 메모리 안의 코사인이다**(`EvaluationRunner`). 운영 경로의 `PgVectorEvidenceRetriever`(`baton.retrieval.max-cosine-distance=0.8`, 키워드 결합, HNSW)는 이 평가 범위 밖이다. 0.8은 stub 기준값이고 실제 임베딩 모델의 거리 분포로 다시 정하지 않았다.
- **256차원 절단은 설계 가정이다(A-13).** 로컬 embeddinggemma에서는 recall@3 100%였으나 OpenAI·Google 모델은 평가하지 않았고, 차원 축소로 학습되지 않은 모델을 고르면 품질이 조용히 무너져도 기동 검사가 막지 못한다. 공급자를 정하면 `aiEvaluation`으로 recall을 먼저 본다.
- **모델 버전이 고정되지 않았다.** `embeddinggemma:latest`는 태그가 움직인다. 측정 하루 뒤(2026-10-06) 이 기계에서 읽은 다이제스트는 embeddinggemma:latest `85462619ee72…`(307.58M, gemma3), qwen3:4b `359d7dd4bcdab3d8…`(4.0B)다. 평가 당시의 값과 같다고 확인하지는 못했다. 읽은 원문(전체 다이제스트)은 [`ollama-models.txt`](ollama-models.txt)에 있고, 두 모델의 수정 시각은 2026-09-30이라 평가(2026-10-05) 뒤에 다시 받은 것은 아니다. 평가와 읽기(2026-10-06 08:23) 사이에 다시 받았다면 다이제스트가 바뀌었을 수 있으나, 수정 시각이 2026-09-30인 것은 그런 재다운로드가 없었다는 정황이라 같은 모델이었을 가능성이 높다. 다만 `modified_at`이 무엇의 시각인지는 확인하지 못했다. 다시 받으면 다이제스트가 바뀔 수 있고, 같은 모델 ID 아래 서로 다른 벡터가 섞이면 검색이 흐려진다. 운영에서는 태그 대신 고정한 모델을 쓴다.
- **평가 원자료는 저장소 안에 있다:** [`w13-ollama-report.md`](w13-ollama-report.md)(위 표의 원본, 실패한 첫 출력 포함).
- **외부 전송 승인은 운영자의 몫이다.** 평가 도구는 `BATON_AI_EXTERNAL_TRANSMISSION=approved`를 스스로 넣지 않는다. 합성 표식은 파일 안의 `synthetic` 값이라 실수를 막을 뿐 변조를 막지 않는다. 토큰 상한은 호출 전에 다음 호출을 막지만 한 호출의 출력 길이는 제한하지 않아, 상한을 넘기는 호출은 최대 하나다.

### 아직 하지 않은 것
- **OpenAI·Google 평가:** 키를 `~/baton-secrets/ai.env`에 넣은 뒤 `BATON_AI_PROVIDER=openai`(또는 `google-genai`)와 모델 ID로 같은 명령을 돌리면 같은 표가 나온다. 외부 단가는 확인하지 못했다(post-cutoff 값이라 추정하지 않았다).
- **동시 부하에서의 AI 지연·실패율**, 실제 문서의 검색 품질, 외부 공급자의 지연과 요청 한도.
- 구조화 실패 원인의 확정(실패 출력을 더 길게 남기는 것이 필요하다).

## 공급자 평가 (2026-10-20)

원본은 [`eval-20261020-openai-report.md`](eval-20261020-openai-report.md)다. 비용: `gpt-5.4-mini`는 입력 100만 토큰당 $0.75, 출력 $4.50이다([OpenAI 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.4-mini)). 채팅 39,342토큰이 모두 출력이어도 약 $0.18이다. 임베딩 단가는 이번에 다시 확인하지 않았지만 3,936토큰이라 결론에 영향이 없다.

읽는 법: 로컬 `qwen3:4b`(구조화 92%, 충돌 60%)보다 모든 지표가 높고 지연은 구조화 p95 1.8초, Q&A p95 1.5초로 README §8 목표 안이다. W13의 한계가 그대로 남는다. 순차로 한 번에 하나씩 잰 값이고, 합성 집합이 쉬워 recall@3 100%가 실제 문서의 품질을 뜻하지 않으며, 프롬프트는 이 집합을 보며 고친 것이다. 잡음 문서 2건에서 기록을 지어냈는데 모두 사람이 확인하는 AUTO_DRAFT로만 남는다. OpenAI 모델의 256차원 절단(A-13)도 이 집합에서는 검색을 해치지 않았다.

### Google: 전체 평가는 못 하고 축소 평가만
- 채팅 `gemini-3.8-flash`, 임베딩 `gemini-embedding-001`로 시작했다. 결과 없이 약 15분 동안 멈춰 있어 스레드를 덤프하니 Google SDK의 재시도 인터셉터(`com.google.genai.RetryInterceptor`)가 요청 스레드를 재우고 있었다. 실행을 멈추고 짧은 요청 하나로 원인을 확인했다. 응답은 429 `RESOURCE_EXHAUSTED`였고, 무료 등급의 `GenerateRequestsPerDayPerProjectPerModel-FreeTier` 한도가 **20회**이며 `retryDelay`는 21,271초(약 5.9시간)였다. 평가는 채팅 호출이 80회(구조화 50, 질문 30) 필요하므로 이 모델로는 하루에 끝낼 수 없다.
- 예비로 정한 `gemini-2.5-flash`는 404 「no longer available to new users」를 돌려줬다. `gemini-embedding-001`은 정상 응답했다(3,072차원, 앱이 256으로 자른다).
- 사용자가 다른 모델로 다시 돌리기로 해(「권고대로 가자」) 채팅을 `gemini-3.7-flash`로 바꿔 같은 명령을 돌렸다. 구조화 단계에서 다시 재시도 대기에 묶였고(90초 넘게 이어지면 멈추도록 감시를 걸어 두었다), 같은 요청 하나로 보니 이 모델도 429 `GenerateRequestsPerDayPerProjectPerModel-FreeTier` **20회**였다(`retryDelay` 8,808초). 두 flash 모델 모두 무료 등급으로는 전체 평가(채팅 80회)를 하루에 돌릴 수 없다.
- 모델별 무료 한도는 공식 문서에 수치가 없고 AI Studio에서만 보인다고 적혀 있다([Gemini API rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)). 그래서 남은 방법은 사용자가 골랐다(아래 축소 평가).
- **축소 평가**(사용자 선택 「축소 평가」): 채팅 `gemini-3.5-flash-lite`, 임베딩 `gemini-embedding-001`, 문서 8·질문 8(채팅 16회, 한도 안). 원본은 [`eval-20261020-google-report.md`](eval-20261020-google-report.md)다.

  읽는 법: Google 공급자로도 구조화·답변·임베딩·256차원 절단이 끝까지 동작한다는 증거다. 표본이 작아(질문 종류별 2문항, 검색 2문항) 정확도와 p95는 OpenAI 전체 평가와 비교할 수 없다. 무료 등급은 무료이므로 비용은 0이다.

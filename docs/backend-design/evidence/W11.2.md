### migration 주석
작업 카드 번호가 남았던 migration 주석은 V10·V13·V14·V15다. migration 파일은 주석을 고쳐도 Flyway 체크섬이 바뀐다. Flyway 12.4.0에서 확인했다: 적용한 파일의 주석 한 줄만 바꾸고 `validate`를 부르면 "Migration checksum mismatch"로 실패한다(runs/scratch-checksum.log, 임시 시험은 저장소에 남기지 않았다). 처음에는 이를 이유로 고치지 않고 예외로 두었다(대장 70).

2026-10-05 사용자 결정으로 고치는 쪽으로 바꿨다. 절차와 확인은 다음과 같다.
- 옛 파일(HEAD)과 새 파일을 각각 새 PostgreSQL 컨테이너에 Flyway로 적용해 체크섬을 구했다(runs/scratch-checksums2.log). 바뀐 것은 4개뿐이다: V10 -1082016421 → 1903567627, V13 -1037945752 → -2038092834, V14 -1513606219 → -127726855, V15 -552580787 → -1702633973. 나머지 V1~V9·V11·V12는 같다.
- 보존 DB 7개의 `flyway_schema_history`를 읽기 전용으로 조회해 이력이 옛 체크섬 그대로임을 확인했다: baton-w10·baton-w10-restore는 V1~V11, baton-w106·w106b·w106c는 V1~V12, baton-w107은 V1~V14, project-baton_db-data는 V1~V10. V15는 어느 DB에도 없었다.
- 갱신(`update flyway_schema_history set checksum = <새 값> where version = <v> and checksum = <옛 값>`)은 이 환경의 자동 권한 검사가 두 번 거부해서 사용자가 직접 실행했다. 실행 뒤 7개 DB를 다시 조회해 V10은 모두 1903567627, baton-w107의 V13·V14는 각각 -2038092834·-127726855임을 확인했다. 데이터와 스키마는 건드리지 않았다.
- load baseline 덤프(~/baton-results/w10.7-baseline/baseline.dump)는 수정하지 않았다. 덤프와 그 지문 파일은 옛 체크섬을 담고 있으므로 `tests/load/baseline.sh restore`가 지문 비교를 마친 뒤 `tests/load/flyway-checksums.sql`을 실행해 맞춘 다음 앱을 올린다. 지문에 체크섬이 들어 있어서 순서를 지문 비교 뒤로 잡았다. 이 스크립트는 실제 복원으로 실행해 보지 않았다(부하 측정 환경을 건드리지 않기 위해). 문장은 사용자가 DB에서 실행한 것과 같은 UPDATE 4줄이다.

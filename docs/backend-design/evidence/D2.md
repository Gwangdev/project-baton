## 체크포인트 리뷰

`/code-review`(high) 6건, 모두 고쳤다(시험을 먼저 추가하고 실패를 확인했다):
- 보존값이 숫자가 아니면 awk에서 0이 되어 방금 쓴 것까지 모든 백업이 지워질 수 있었다 → 1 이상의 정수가 아니면 거절(월간은 0 이상, 빈 값은 기본값).
- NAS가 마운트되지 않으면 빈 마운트 지점(이 호스트의 디스크)에 조용히 썼다 → 대상 폴더의 표식 파일 `.baton-backup-target`이 없으면 거절(표식 검사를 빼는 변이에서 시험이 실패).
- umask 077이라 리눅스에서 운영자가 복원 연습 때 백업을 읽지 못했다 → 640, 폴더는 소유자 999·운영자 그룹·setgid(README).
- 겹친 실행이 서로의 `.partial`을 지울 수 있었다 → `flock` 잠금, 다른 실행이 쥐고 있으면 거절.
- 복원 연습이 macOS의 `shasum`에만 기댔다 → `sha256sum`이 있으면 그것을 쓴다.
- 기반 이미지는 digest로 고정했는데 `age`는 버전을 고정하지 않았다 → `age=1.1.1-1+b3`.

## 확인한 것

- macOS Docker Desktop에서는 권한 700의 홈 폴더에도 uid 999 컨테이너가 쓸 수 있고 파일은 사용자 소유로 보인다. 리눅스 운영 호스트에서는 폴더 소유자를 999로 맞춰야 한다(README에 적음).
- 임시 Compose 프로젝트(`baton-d2check-*`)로 `--profile backup`의 `run --rm backup once`가 지정 폴더에 백업을 쓰는 것을 확인하고 프로젝트를 `down -v`로 지웠다. 보존 스택과 volume은 건드리지 않았다.
- 기존 스택(`compose.yml` 단독, `compose.dev.yml` 오버레이)의 `config`는 그대로 통과한다(백업 변수가 없어도 됨).

## 사용자 키로 한 백업·복원 확인(2026-10-16)
- 사용자가 README 절차로 age 키를 만들었다. 개인키는 저장소 밖 폴더와 비밀번호 관리자 두 곳에 있다. 메인 세션은 키 내용을 읽거나 출력하지 않았다.
- 연습용 스택(`baton-backup-trial`, DB와 앱만, 기존 앱 이미지라 Flyway 19)을 띄워 `backup` 서비스로 한 번 백업했다(`baton-backup once`, 사용자 공개키, `~/baton-backups`): 136 KB 암호화 파일과 SHA-256.
- 개인키로 `tests/recovery/restore-drill.sh`를 원본 지문과 함께 돌렸다: 31개 테이블, 19행, Flyway 19, 지문 일치.
- 연습용 스택은 지웠고, 컨테이너·volume 이름 목록은 시작 때와 같다. 백업 파일은 남겼다.
- 상시 야간 백업은 켜지 않았다. 이 Mac에는 상시로 도는 Baton 스택이 없고, 야간 일정은 배포 환경에서 `--profile backup`으로 켠다.

실패 테스트가 잡은 구체적 반례(모두 테스트를 먼저 쓰고 실패를 확인한 뒤 고침):
(1) 워커 6개가 Spring 기본 스케줄러 스레드 1개를 나눠 써서, README §6의 구조화/패키지 6·임베딩 1 slot이 실제로는 합쳐 1개였다. lease heartbeat도 없었다. JobSlots(slot을 먼저 확보한 뒤 claim, 공유 slot은 lane을 번갈아 선택해 한쪽이 밀려 굶지 않게, 큐가 비면 tick당 runner 하나만 확인)와 LeaseHeartbeat(10초마다 30초 lease 갱신, 토큰이 바뀌었거나 deadline이 지나면 갱신 안 함)로 고쳤다. JobSlotsTest가 동시 실행 상한 6, 공유 slot 공정성, 예외 뒤 slot 반환, 빈 큐 확인 횟수를 잡는다. LeaseHeartbeatIT가 갱신, deadline 이후 중지, 빼앗긴 lease, 처리기 예외 뒤 해제를 잡는다.
(2) 수집 워커가 1초에 INGEST 한 건만 처리했다. 1,200개 연결을 5분마다 적재하면 초당 4건이 필요한데, seed 뒤 991건이 밀려 있었다. 수집에 전용 slot(1개, AI slot과 별개)을 두고 큐가 빌 때까지 처리하게 했다. IngestionWorkerIT에 「dispatch 한 번에 연결 20개의 INGEST가 모두 끝난다」를 추가했다. 부하 시험 중 INGEST 21,631건의 p95는 1.9초였다.
(3) 로그아웃 때 Set-Cookie가 두 번 나갔다. Spring Session이 이미 같은 serializer로 만료 쿠키를 쓰는데, 수동으로 만든 쿠키(Secure 없음, semgrep 지적 자리)를 한 번 더 붙였다. 수동 쿠키를 지웠다. AuthenticationIT가 쿠키가 정확히 하나이고 Max-Age=0·Secure·HttpOnly·SameSite=Lax·Path=/인지 확인한다. CSRF 쿠키의 Secure는 저장소 bean으로 검증한다. MockMvc의 csrf() 후처리기가 필터의 저장소를 테스트용으로 바꿔치기해, 요청으로 검증하면 테스트 순서에 따라 결과가 달라지기 때문이다. LocalHttpCookieIT는 스위치를 끈 경우 Secure가 빠지고 나머지 속성은 남는지 확인한다.
(4) 관리 포트에도 기본 보안 체인이 적용돼 probe가 401이었다. /actuator/** 전용 체인(@Order 1, health·prometheus만 허용)을 두었다. ManagementEndpointsIT가 liveness 구성 {livenessState}, readiness 구성 {readinessState, db}, slot gauge, 식별자 태그 없음, 공개 포트에서 actuator 불가를 확인한다.
(5) work_records.source_note_id 인덱스가 DBML에는 있는데 V1 migration에 없었다. 90만 건에서 메모 목록이 요청마다 전체 스캔으로 약 1초 걸렸다(EXPLAIN ANALYZE: Seq Scan on work_records rows=900000, 1,021ms). V11 부분 인덱스를 추가했다. SchemaIT가 V11 없이 실패하고 있으면 통과하는 것을 확인했다. 부하 스택에 적용하는 데 1.2초 걸렸다.
(6) 관리 화면과 확인 대기함이 명령 뒤 목록을 다시 받기 전에 버튼 잠금을 풀었다. 그 사이 클릭은 옛 version을 보내 412가 났다. 실제 백엔드 E2E에서 처음 드러났다. 재조회가 끝난 뒤 잠금을 풀도록 바꿨다. 단위 테스트는 재조회가 끝나기 전 삭제 버튼이 잠겨 있는지 확인한다.
(7) Hikari connection-timeout을 "5s"로 두면 기동에 실패한다(HikariConfig는 long 밀리초로 바인딩). 5000으로 고쳤다. DB가 멈췄을 때 readiness가 기본 30초 대기에 걸리던 것을 줄이는 목적이다.

(d) FailureIsolationIT가 비밀번호 리터럴을 새로 두어 게이트 X1 항목에 파일이 하나 늘었다. 실행마다 생성한 값으로 바꿨다. 검증: 가짜 docker·curl로 (a)~(c)가 고치기 전 실패·고친 뒤 통과함을 확인(실제 Docker 자원은 건드리지 않음), seed.sql 머리말은 baton-w10 DB에서 쓰기 없는 쿼리로 설정·미설정 두 경우 확인, FailureIsolationIT 3 tests 통과, gate --commit BLOCK 9 유지(X1은 기존 QaTestSupport만 남음).
- 미결: JobSlots.destroy()가 실행 중 job을 인터럽트하고 기다리지 않아, 재기동마다 진행 중 job이 lease 만료 뒤 재시도되며 시도 횟수 하나를 쓴다. 계약(W05)은 프로세스 종료를 lease 회수로 처리하도록 정했고 정상 종료 대기 시간은 정하지 않았으므로 /design 판정이 필요하다.
- 안 고침(영향이 작음): JobSlots의 idle 플래그를 runner들이 공유해, 새 backlog의 첫 job이 도는 동안에는 tick당 runner를 하나씩만 더한다. 최대 5초 늦게 6개가 차며 구조화 p95 30초 기준 안이다.
- 성능 카드 입력: runner가 큐를 비울 때까지 돌면서 claim마다 sweep UPDATE 5개와 releaseAbandonedSources(STRUCTURE job 전체 DISTINCT ON)가 job 수만큼 실행된다.
- 제안(채택 선택): LeaseHeartbeat의 30초 lease SQL을 JobLeaseService로 옮겨 한곳에 두기. SecurityConfig의 cookie-secure 기본값 선언 세 곳을 하나로.
- 보안 수동 점검 결과 이상 없음: 쿠키 Secure 기본 true(false는 e2e·compose.dev만). 관리 체인은 health·prometheus만 허용하고 관리 포트는 게시되지 않는다. 데이터 계층은 internal 네트워크에만 있다. forward-headers native는 사설 대역을 신뢰하지만 8080에 닿는 것은 proxy뿐이고, Caddy는 신뢰하지 않는 클라이언트의 X-Forwarded-* 값을 버린다(caddyserver.com/docs/caddyfile/directives/reverse_proxy). 프록시 없이 앱 포트를 직접 여는 구성에서는 X-Forwarded-For로 로그인 제한기를 우회할 수 있으므로 그런 배포는 하지 않는다.

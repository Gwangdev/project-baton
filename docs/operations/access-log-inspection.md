# 접속기록 점검 절차

개인정보의 안전성 확보조치 기준 제8조 ②은 개인정보취급자의 접속기록을 확인·점검하는 주기·방법·사후조치를 내부 관리계획으로 정하고 이행하라고 요구한다. 주기·방법·사후조치는 도입 고객사가 정한다. 이 문서는 Baton이 그 점검에 내주는 기록과 조회 방법을 적는다. 시스템에는 운영자용 접속기록 화면이 없어 DB를 직접 조회한다(대장 199).

## Baton이 남기는 기록
`audit_events` 한 행이 행위 하나다: 행위자(`actor_id`), 행위(`action`), 대상(`target_type`, `target_id`), 결과(`result`), 추적 ID(`trace_id`), 시각(`occurred_at`), 요청 주소(`remote_address`, 로그인과 설정 코드 행위만).

- **남는 것:** 로그인 성공(`SIGN_IN`), 계정·설정 코드·비밀번호 설정, 조직·사용자·프로젝트·구성원·연동의 생성·수정·삭제, 기록 검토·관계 등록·철회, 개인 메모 공유, 인수인계 요청·재생성·보완 요청·승인. 행위 종류는 `access-log-queries.sql`의 5번이 기간별로 보인다.
- **남지 않는 것:** 실패한 로그인, 조회(기록 상세·목록, Q&A, 인수인계 열람). 개인정보를 내려받는 기능은 없다. 이 범위가 고시가 말하는 접속기록에 충분한지는 고시 제2조(정의) 원문으로 확인해야 한다(대장 208).
- **보존:** 감사 행은 지우지 않는다. 로그인 행의 요청 주소만 24개월 뒤 비운다(스위치 `baton.retention.audit.*`, 기본 꺼짐). DB가 감사 행의 삭제와 그 밖의 수정을 거부한다(V21, D5).
- **공개 데모는 예외다.** 합성 데이터 데모(`baton.gwang.dev`, D7)는 매일 04:00 기준 덤프로 DB를 통째로 되돌리므로 감사 행과 방문자의 접속 주소도 그때 사라진다. 로그인 화면과 README가 이를 알린다. 실제 도입 배포에는 이 초기화가 없다.

## 조회 방법
DB에 접근할 수 있는 운영자가 [`access-log-queries.sql`](access-log-queries.sql)을 점검 기간과 함께 돌린다. 모두 읽기만 한다.

```bash
docker compose --env-file ~/baton-secrets/stack.env exec -T db psql -U baton -d baton -v from='2026-10-01 00:00+09' -v to='2026-11-01 00:00+09' -f - < docs/operations/access-log-queries.sql
```

| 번호 | 보는 것 |
|---|---|
| 1 | 기간 안의 로그인(사번, 이름, 요청 주소) |
| 2 | 서울 기준 평일 08:00~20:00 밖의 로그인 |
| 3 | 한 계정이 여러 주소에서 로그인한 경우 |
| 4 | 계정·권한을 바꾼 관리 행위 |
| 5 | 행위 종류·결과별 건수 |

로컬 구성(`compose.yml`)의 `baton` 계정은 DB 슈퍼유저다. 공개 데모 배포(`compose.deploy.yml`)에서는 감사 테이블과 사용자 테이블만 읽는 `baton_inspect`로 연결한다(`-U baton_inspect`, 비밀번호는 `/etc/baton/deploy.env`의 `BATON_DB_INSPECT_PASSWORD`).

## 점검 기록(고객사 내부 관리계획의 예시, 가정)
- 주기: 월 1회 [가정 — 고객사가 정한다].
- 확인: 1~5번의 결과에서 퇴사·휴직자 계정의 로그인, 업무 시간 밖 접속, 낯선 주소, 계획되지 않은 관리 행위.
- 사후조치: 발견하면 고객사 보안 담당에게 알리고, 계정은 관리 화면에서 비활성화한다. 점검 일자·범위·결과·조치를 고객사 양식에 남긴다.
